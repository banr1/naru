## 人間への問い
**C73 の claim `finalized` の「判定 1 以上」をどう扱うか。**

**事実**
- `finalized` の前提 `FinalityRegime` は `t0 + finalityStartup(s, gap) <= horizon` を含む。
- `finalityStartup` を Lean で評価すると、前提を満たしうる最小の設定(gap 3・k 5・r 1・d 0・Δ 1)でも 2279、固定設定で 6159〜7863 だった。
- 生成 Model の run は horizon 600 で 103 秒かかり、費用は 3〜4 乗で増える。「今回の周回の運び」が許す長い horizon の少数 run も、群の予算 5 分に収まらない。
- 検査器・前提の判定器・負の検体は置いた。結論の経路は、startup と期限を差し替えた負の検体で判定 403・違反 0 を確かめた。
- それでも固定設定の判定は 0 で、C73 の検証「前提を満たし byzantine を含み期限が horizon 内に収まって実際に判定された件数が検査器ごとに 1 以上」を満たせない。
- 現在のドライバは理由が horizon に限られるときだけ `pending:` の行を出して exit 0 にしている。C73 は unmet のまま。

**選択肢**
- **(A) 強い形で判定する(`hreadBound` と同じ扱い)【推奨】**
  - 期限を外した強い形を判定の形にする。具体的には「GST 以後の honest な提案は `4 · period`(Δ = 1 で 48)以内に honest 全員の finalized の読みに入り(`IncludedFrom(Finalized, tGST, 4 · period)`)、同じ期限で `LiveFrom` が成り立つ」。
  - 手書きの期限付きの形は判定外として併せて数える。
  - 強い形の違反は「期限の前の正常な挙動」に分けられる。
  - 実測の遅れは最大 40(Δ = 2 で 81 < 96)で、固定設定で判定が数百件出る見込み。finality の進行についての実質的な反例探索になる。
  - IDEAL.md の C73 の「強い形」の対象に `finalized` を加え、強い形の期限(例: `4 · period`)を書いてもらう必要がある。
- **(B) `finalized` だけ「判定 1 以上」を外す**
  - 判定外の件数・負の検体・違反 0 だけを要求する。現在の実装のままで C73 の検証に合う。
  - ただし finalized の結論は固定設定の run では一度も判定されない。
- **(C) 長い horizon の run(2279 以上)を別モードで走らせる**
  - 費用の見積りは 1 本で数時間〜数日で、回帰には入らない。C73 の「判定 1 以上」は回帰の固定設定で要求されているので、C73 の文面の変更も要る。

**推奨の理由**: (A) を推奨する。周回197の `hreadBound` の答えと同じ形で、実行可能な horizon で finalized の振る舞いを実際に判定できる。

**決めないと止まるもの**: C73 は met にならない。C36 の到達(C73 を含む)も止まる。C74 は、`finalized` の検査器の形が定まらないと theorem の形が決まらない。

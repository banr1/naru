## 申し送り
C20 は met になり、エディタ対応 C16〜C20 はすべて met。必須の残りは C7〜C10(周回 10 の記録の (a)(b)(c) の設計の申し送りが有効: scenario / observer / protocol 宣言の意味、stdlib の generic な Event / Run、`simulate` の runner、Statements backend、同一プログラムの golden test)。次の周回は周回 10 の記録と台帳の C7 / C10 の備考を読み、依存の根に近い C7(`lake exe naru simulate dsl/scenarios/basic.naru`)から着手する。コードを変えた周回は知見の回帰一式(17 本)を通して met 条件の `cycle N:` を取り直す。
`observed 15:`(C20)は対象ファイルを変えた周回とそれ以後の出典が失効する(`observed N:` は N ≤ C で失効)。実装周回の間は取り直さなくてよい(progressed は受理される)が、必須がすべて met になったら、対象ファイルを変えない周回を 1 つ置いて knowledge「C20 の観測」の手順(約 1 分)で `observed N:` を取り直し、その周回で realized にする。`editors/`・`compiler/Naru/Lsp.lean`・`highlights.scm`・`rev` を変えた周回の次の周回も、画面が実際に変わりうるので取り直す(`rev` を付け替える周回は `naru_test zed` → `naru_test zed-install`(rebuild 経路)→ 次の周回で C20 の順)。`naru_test zed-install` は回帰一式に入れない。
C20 の観測を `cycle N:` の形(Lean の検査ドライバ `naru_test zed-open` のような、`zed -n` → Zed.log → 画像の存在と状態行の照合)にする案はあるが、画像の読み取り(色・波線)は機械検査にならないので `observed` のままでよい。作るなら対象ファイルを変える周回で。
IDEAL.md の事実との差(ask にはしない。周回 14 から継続): C19 の括弧書き「installed 側のパスを引用符なしで」は Zed 1.23.2 では「rebuild は installed 側のパス、install はソースのパス、どちらも引用符付き」。前提の「`~/.cargo/bin`」は cargo の実体が `/opt/homebrew/opt/rustup/bin`。用語の `naru_test` の群に `zed-install` が増えている。前提の `sort(set, by = …)` と C11 の `by` の grep の潜在的な矛盾も周回 2 から継続。

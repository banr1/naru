## 選択
C10 に向けた移植の次の塊として、依存順に ValidatorClient + Grades + Head + Duties/Inputs(手書き 1,132 行)を選んだ。理由: (1) 必須の unmet はすべて移植が根で、この先の Proposals / Store / Handlers はすべて GradeContract(= Cache)と HealingStore・NamedRecord に依存する(依存の根に最も近い)。(2) C1 / C6 はその出力で同じ周回に取り直せ、手書き Protocol 層の olean(Duties.Inputs まで)があるので値の一致(golden test の予行)まで観測できる。(3) 言語機能の追加が要らない見込みだった(実際に要らなかった: 関数型の仮引数・Table / Set・tuple・構造的再帰・fuel で足りた)。周回 7 の申し送りは Grades → Head → Inputs の順で ValidatorClient を後に置いていたが、ValidatorClient は Goldfish と NamedBlocks にしか依存せず小さいので同じ周回に含めた。
設計の判断(IDEAL.md「移植の対応」の範囲。言語・stdlib・検査は変えていない。各ファイルの先頭コメントに明記): `Record` の関数欄(`Height → Option BlockId` / `Height → Bool`)→ `Table<Height, BlockId>` + `get?` / `Set<Height>` + `contains`(`with_*` は `insert`)。`GradeContract`(関数欄の record)と `ConfirmationSGCandidate`(関数を包む inductive)は Model に instantiation が `frameContract c` の 1 つだけ(Execution/Node の `gradeContract`)なので inline し、手書きの `contract` 引数は `c: Cache`(`contract.read` → `frameGradeRead`、`sgVote` → `currentSGVote`、`confirmationSG` → `frameSgCandidate`、`stableRoot` → `frameStableRoot`)。`GradeRead.clear : Block → Bool` は読んだ frame を欄 `frame` に持ち `clear(grades.frame, b)`、`rawG2 : Prop` + `Decidable` は Bool。`Token (Key)` は `Option BlockId` に固定、`Supports` / `Opposes` / `CleanFrom` は `any` / `all` と `!p || q` で Bool に。`Finset.univ.filter p` → `validators(e.electorate).filter(p)`(外の validator は重み 0 で和は同じ)。`HealingStore extends FGStore`(欄なし)→ `type HealingStore = FGStore`。`with_proposal_input` / `with_attestation_input`(継続渡し、型引数 `Result`)→ `ProposalInput` / `AttestationInput` を返す fn(`use` は呼出し側で適用)。`Phase` は stdlib の Event の phase と名が重なるので `GradePhase`。`HealConfig` の証明欄 `R_ge_three` / `η_SG_ge_one` は Statements の premise(`HeightConfig` と同じ)。`fgToGoldfish`(`st.toFG.toSG.toGoldfishStore`)を Goldfish.naru に 1 つ足した。

## コンパイラの事実
- 段: 字句解析 → 構文解析 → 名前解決・phase 検査(`Resolve.lean`: E001, E011〜E013)→ 型・capability 検査 + Core IR への elaboration(`Typecheck.lean`: E003〜E006, E014〜E016。`infer` が `(型 × Core.Expr)` を返す)→ 停止性検査(`Totality.lean`: E002。受理した再帰の測度を backend に渡す)→ Model backend(`Backend/Model.lean`: E017)。前の段に誤りがあれば次の段には進まない。`import` は受理するだけで検査しない(存在しないモジュールを import しても診断は出ない)。
- Core IR(`Core.lean`)は型付き・名前解決済み・糖衣展開済み。`TyV` はここで定義(型別名は展開済み、メタ変数は Core には残らない: 残れば E014)。
- stdlib メソッドの追加は 3 箇所: `Typecheck.lean` の `*Sigs` 表(型変数 `$T` `$K` `$V` `$E` は受け手で束縛、`$U` は呼出しごとに fresh)、`Backend/Model.lean` の `emitMethod`(Lean core の名前か `NaruStd.*`。`Table` / `Set` は `NaruStd.Table.<名前>` に自動で落ちるので NaruStd に def を足すだけ)、`SYNTAX.md` の表(+ `tests/accept/backend.naru` に受理例)。Lean 4.34.1 の `List.flatMap` / `List.filterMap` は関数が先の引数順。
- E002 が受理する再帰は 2 形だけ: match の構築子パターンで取り出した部分項への構造的再帰(再帰呼出しが別の fn / stdlib メソッドの実引数の中にあってもよい)と、`n ≥ k` が分かる分岐内で Nat 仮引数(または match の bind 別名)を `n - k` で渡す fuel。下限は `if` の条件(比較とリテラル、`!`、`&&` の then、`||` の else、`else if` の連鎖)と、`match n` のガード無しリテラル腕(0 から連続して覆った値の次)と腕のガードから取る。サイクル(相互再帰)は全辺で同じ測度が厳密に減ること。`let` 経由・record の欄・lambda 内・Int・関数値の受け渡し・辞書式の測度は E002(保守的)。lambda の中から再帰しない fn を呼ぶのは自由。
- 関数型の仮引数(周回 6): `fn f(score: (Block) -> Nat, …)`、多引数も可。`Ty.fn` は fn / observer / spec 宣言の仮引数・closure の引数・`let` の注釈にだけ許す(欄・variant・別名・戻り型・input・コレクションの中・`() -> U` は E014)。本体の `score(b)` は Core の `callLocal`。`let score: (Block) -> Nat = |b| …;` と注釈付きで lambda を束ね、呼び・捕獲させ・関数型の仮引数に渡せる。停止性: 関数値の呼出しは辺にならず、fn を値として参照した場所が `bare` 辺になるのでサイクル内なら E002。backend は `(«score» : (A → B))` と `«score» b` を出す。`_e` のような未使用の仮引数は Lean の警告にならない。
- backend が Lean に落とす形は SYNTAX.md「Core IR と Model backend」。fuel は `if _h' : c` + `termination_by n` + `decreasing_by …`、`Nat` の match は `match _hm' : n with`、ガードは Option の match、構造的は `termination_by structural p`。宣言は参照の依存順に並べ替えて出す(ソース内の前方参照は可)。引数 0 個の fn(`initialNode()`)は Lean では値 `def initialNode : NamedNodeState`。`input` を(推移的に)使う fn は先頭に `名前'` の関数引数を持つ(完全修飾名の辞書順: `storeAt (committee' proposer' awake' newRoot')`、`postCore (committee' proposer')`、`wellFormed (committee')`。生成ファイルの `def` の先頭行で確かめる)。生成コードの Lean 組み込み名は完全修飾、局所名・欄名は `«»`。
- 名前解決はコンパイル単位(渡された全ファイル)を 1 つの大域表で行う。`import` は受理するだけで意味を持たない(backend はモジュール間の参照から `import` を計算し、循環は E017)。同名の fn はファイルが違っても E012(移植では `named…` / `sgTo…` / `storePool` / `initStore` / `nodeTick` のように改名して逃げる)。欄名・enum の variant 名は大域表に入らないので fn や型と同名でよいが、Lean が生成する名前(`rec` `mk` `casesOn` …)は欄名に使えない(E012。`record` も予約語なので `signing`)。仮引数・lambda 引数は同名の大域 fn を隠す。予約語(`input` `record` `module` `state` …)は局所名にも使えない(`inp` / `rec` / `post`)。
- 大文字始まりの経路は大域名(`Phase.Tick`、`Set.empty`)、小文字始まりは値と欄の連鎖。局所名は小文字か `_` 始まりのみ(大文字は E010)。`x.f(args)` は `f` がユーザ宣言の大域名なら `f(x, args)`(UFCS)、無ければ stdlib メソッド。record literal は `if` の頭部に直接書けない(`let` に束ねる)。`type Alias = Record` / `type Alias = Table<K, V>` は型の位置でどこでも使え、メソッドは展開した型で解決する(`NamedWorld = Table<ValidatorId, NamedNodeState>` に `getOr` / `insert`)。literal / update は元の record 名で書く。record literal の入れ子 update は可。
- tuple は n 要素(`(A, B, C)` → Lean の右結合 `A × B × C`)。パターンは入れ子可。tuple の射影は無いので戻り値の組は `match f(x) { (a, b) => … }` で取り出す(match の腕の中に `match` を直接書いてよい)。`match` の scrutinee には `if` 式も置ける。`match (a, b) { … }` の網羅性は Lean が検査する。
- 組み込み: primitive 型名、`Some` `None` `Ok` `Err`、自由関数 `sort` `choose` `pick`(再宣言は E012)。`unknown` 型は診断を出した後にだけ作る、が不変。Int リテラルは Int が期待される位置で Int。
- capability: `eq` は primitive と derive eq の record/enum とその合成、`order` は Nat/Int/String・Option/List/tuple・derive order の record/enum(tuple の順序は辞書式: Lean の `lexOrd`)。Set/Table/関数型は order も eq も持たない。Set → List は `sort(by = …)` だけ。`Set.sum` / `List.sum` と `Set.flatMap` は Set から直接取れる。`List.flatMap` / `List.filterMap` / `Table.mapValues` は周回 9。メソッドの cap 検査は受け手の型で即時、`Set.of` / `Set.singleton` の要素の `eq` は宣言の終わりに検査する。backend は `eq` に `DecidableEq` と隠れた `Ord` を、`order` に `Ord` を、常に `Repr` を生成する。
- `Naru.sha256Hex`(`Sha256.lean`)は Lean 実装。`shasum -a 256` と一致を確認済み。コンパイラの版 `naruVersion`(`Main.lean`)は `lakefile.toml` の `version` と合わせる。stdlib の hash は `stdlib/Model/**/*.lean` の内容から計算する(版は目印)。

## Lean 4.34.1 の癖
- `syntax` と `meta` は予約語。`String.mk` は非推奨。docstring `/-- -/` は `mutual` の前に置けない。到達しない match の alternative は **error**。`deriving DecidableEq` / `Ord` は入れ子の帰納型(`Option<Self>` 越し)に使えない。`{ x with }`(欄なし)は使わず `x` を出す。
- 手書き側の fixture: `{ fg with sg_votes := …, live_confirmed := b3 }` のように `extends` 越しの親の欄も `with` で直接更新できる。`GradeRead`(`rawG2 : Prop` + `rawG2_decidable`)は作り直す(`⟨anchor, none, clear, False, inferInstance⟩`)。`CleanFrom` には Decidable instance が無い(test 側に `instance … := by unfold CleanFrom; infer_instance`)。`Finset.sort` / `image` / `biUnion` は `#eval` できる。`Setup` の証明欄は `node_val_index := by intro v; rfl`、`timeout_rounds` / `outage_window` は `by decide`、`committee_nonempty := by intro s; change ({0} : Finset (Fin 2)).Nonempty; exact Finset.singleton_nonempty 0`(`{ S with E := … }` は証明欄が E に依存するので使えない: 全欄を書き直す)。

## 環境の癖
- Bash から `.idd/` や `IDEAL.md` に触れる(ls を含む)とフックが拒否する。リポジトリのルートで引数なしの `ls` を実行すると(`.idd/` が含まれるため)コマンドが戻らず timeout になるので、`git ls-files` やサブディレクトリの `ls` を使う。記録・台帳は Write ツールで書く。`rm -rf` を含むコマンドも拒否されうる(出力先は毎回別名の一時ディレクトリにするか、`compile` 自身の作り直しに任せる。Lean の `IO.FS.removeDirAll` は使える)。
- 一時的な naru ソースの実験は `/tmp/naru-tc/*.naru` に置き、`lake exe naru compile [--out /tmp/naru-gen] /tmp/naru-tc/x.naru` で検査・生成できる(リポジトリ外でも可)。新しい書き方は本番ソースに入れる前にここで 10 行の probe を通すと速い。手書き側の計測は `lake env lean -Dprofiler=true -Dprofiler.threshold=2000 <file>` で command ごとの時間が出る。
- 同じワークスペースで `lake build` / `lake exe` / `lake env lean` を同時に 2 つ走らせない(`.lake` のロック)。ルートと `verified-consensus/` は別ワークスペースなので、手書き側の長い `lake env lean` の間にルートの `compile` / check-reject は回せる。subagent に lake を使わせる間は自分は実行しない(reviewer には「lake を実行しない」と明示して tree-sitter CLI だけを使わせると並行できる)。長い回帰はバックグラウンドで 1 本にまとめる。
